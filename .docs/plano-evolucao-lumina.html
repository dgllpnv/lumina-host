Diagnóstico — onde o Lumina está hoje

O backend (Express + Prisma + Postgres) já tem a espinha dorsal certa: multi-tenant por organizationId, RBAC de três papéis, e CRUD completo para reservas, quartos/mesas, financeiro e estoque. O que falta não é reescrever — é estender três pontos específicos que hoje são rígidos demais para um produto com vários clientes de perfis diferentes.

a.Tipo de estabelecimento é binário e não controla a interface

Hoje Organization.tipo aceita só "restaurante" ou "pousada" (AdminOrganizations.tsx:51), e o menu lateral (AppSidebar.tsx:24-38) mostra PDV Restaurante e PDV Hotel para todo mundo, sem checar o tipo. Uma pousada pura hoje veria um item de menu de restaurante que não deveria nem existir para ela.

b."Ativo" existe, mas não é gestão de contrato

Organization.ativo é um booleano solto — não há data de início/fim de vigência, plano contratado de forma estruturada, nem um histórico do que aconteceu quando o contrato foi suspenso. Isso é o suficiente para "ligar/desligar" um cliente, mas não para o super admin gerenciar contratos de verdade.

c.Não existe conceito de "site público" ligado a uma organização

O Lumina hoje é 100% um painel interno (autenticado). Não há nenhuma rota pública, nenhum endpoint de leitura sem login, e nenhuma noção de "conteúdo de vitrine" (fotos, descrições, pacotes, dicas) — só dados operacionais (reserva, quarto, preço-base). O site da Algas Marinhas foi construído no Claude Design como uma peça isolada, com dados digitados à mão — exatamente o padrão que não queremos repetir cliente após cliente.

Leitura A boa notícia: o modelo de dados (TableRoom, Reservation) já cobre quartos, tipos, capacidade, preço-base e status — a base para alimentar um site público já existe. Falta a camada de conteúdo de marketing (fotos, descrição longa, pacotes, dicas) e a camada pública que expõe isso.
01

Visão de produto — o que muda

Três mudanças estruturais, nesta ordem de dependência: primeiro o cadastro do super admin fica correto, depois o modelo de dados ganha a camada de "vitrine", só então o site de cada cliente passa a ser gerado a partir do Lumina em vez de escrito à mão.

1.Cadastro de cliente com tipo de negócio

No cadastro do super admin, três opções mutuamente exclusivas — Pousada, Pousada + Restaurante ou Restaurante — e a interface (menu, módulos, PDV) se adapta:

Tipo escolhidoMódulos visíveisMódulos ocultos
PousadaPDV Hotel, Reservas, Site de reservas, Financeiro, Estoque, EquipePDV Restaurante
Pousada + RestauranteTodos os módulos—
RestaurantePDV Restaurante, Financeiro, Estoque, EquipePDV Hotel, Reservas, Site de reservas

Tecnicamente: trocar tipo de dois para três valores (pousada | pousada_restaurante | restaurante) e mover a lógica do menu de "estática" para "derivada do tipo da organização ativa" — a mesma useOrganization() que já existe hoje.

2.Gestão de contrato, não só um interruptor

O super admin passa a registrar vigência (data de início, data de fim/renovação), plano e status (ativo / inativo / inadimplente) por organização. Quando um contrato fica inativo, o painel interno bloqueia acesso — e, criticamente, o site público do cliente também deve refletir isso (ex: mostrar "temporariamente indisponível" em vez de manter reservas abertas para um cliente que saiu).

3.Site público como "vitrine" do mesmo dado, não um projeto à parte

Cada pousada cliente ganha uma página de reservas pública, com o mesmo visual/estrutura provada no site da Algas Marinhas (ver seção 05), mas alimentada por uma API pública de leitura do Lumina — fotos, tipos de quarto, tarifas, pacotes e dicas ficam editáveis pelo admin da pousada dentro do próprio painel, e aparecem no site sem precisar tocar em código a cada cliente novo.

Padrão para escalar clientes Este é o ponto que vira processo replicável: o site de reserva de cada cliente é um "tema" sobre o mesmo motor (dados + disponibilidade + checkout), não um artefato único por cliente. Algas Marinhas define o layout de referência; os próximos clientes reaproveitam o motor e recebem apenas identidade visual e conteúdo próprios.
02

Integração com Booking.com e o site do cliente

Pesquisa de mercado (Cloudbeds, Mews, SiteMinder, Channex, e documentação de parceiros do próprio Booking.com) aponta um padrão consistente e uma restrição real que muda o plano.

a.O que os melhores PMS fazem

  • PMS como fonte única de verdade. Tarifas, disponibilidade e restrições nascem no PMS e são empurradas para todos os canais — nunca o contrário. O site próprio do hotel lê a mesma disponibilidade que os canais externos, para nunca ficar "dessincronizado do próprio dono".
  • Sincronia por API/webhook, não por importação manual. Reservas chegam de volta via webhook (preferível) ou polling curto — minutos de atraso já é risco real de overbooking em alta ocupação.
  • Channel manager como camada separada, não uma feature do PMS. Mews e a maioria dos PMS modernos não certificam a conexão com cada OTA eles mesmos — eles conectam a um channel manager (a SiteMinder, no caso da Mews) que já tem certificação com 400+ canais.

b.A restrição real: Booking.com direto não é opção agora

Achado da pesquisa A Booking.com está atualmente pausando a homologação de novos provedores de conectividade — ou seja, o Lumina não consegue (e não deveria tentar) virar um "channel manager certificado" direto com a Booking.com nesta fase. Além disso, a sincronização via iCal só é permitida para propriedades que não usam nenhum PMS/channel manager, e a própria Booking.com não sincroniza iCal entre múltiplos quartos da mesma propriedade — não resolve o caso de uma pousada com vários tipos de quarto.

O caminho realista, usado por PMS pequenos e médios no mercado inteiro, é integrar via um channel manager white-label — eles já têm a certificação com a Booking.com e revendem a conectividade via API REST para quem constrói o PMS por trás. O Lumina integra uma vez com o channel manager; o channel manager já resolve Booking.com, Airbnb, Expedia etc.

c.Qual channel manager — revisado por custo

Primeira proposta foi o Channex, mas a partir de US$ 130/mês de plano mínimo não faz sentido para um Lumina com um cliente só. Comparando as alternativas reais do mercado:

d.E a opção gratuita? Duas foram verificadas a fundo

Como quem constrói essa integração é o próprio time do Lumina (sem custo de mão de obra terceirizada), o único custo real em jogo é a assinatura recorrente do fornecedor. Duas rotas genuinamente gratuitas foram investigadas antes de fechar a recomendação:

  • NOBEDS (parecia a resposta certa, não é): tem um tier "free" de verdade (€0, até 10 quartos, 3 canais), mas o tier gratuito não inclui API — é só um painel isolado, sem forma de conectar ao Lumina. Acesso à API só existe no plano de US$ 99/mês, mais caro que o Beds24. E reviews independentes relatam bugs de dupla reserva — exatamente o risco que uma integração de channel manager existe para eliminar. Descartado.
  • iCal nativo da Booking.com (o único caminho de US$ 0 real): sem fornecedor terceiro, sem custo, sempre disponível. Mas é uma integração fraca: só bloqueia datas (sem nome do hóspede, contato, valor ou forma de pagamento), atraso de sincronização de até 12h, e só funciona enquanto a propriedade não usa nenhum PMS/channel manager certificado — se a Beds24 entrar depois, o iCal precisa ser desligado. Também exige no máximo 1 unidade por tipo de quarto (a confirmar com a Algas Marinhas, mas plausível para uma pousada pequena).
Recomendação final Beds24 continua sendo a melhor escolha — não porque as alternativas gratuitas são inviáveis por serem gratuitas, mas porque nenhuma delas entrega uma integração boa pelo mesmo dinheiro (ou por menos). A US$ 9/mês por propriedade, é mais barato que a única opção gratuita com API (NOBEDS a US$ 99/mês) e entrega o que uma integração de verdade precisa: dados completos da reserva, sincronização em minutos, não em até 12 horas. Sugestão de sequência: usar o iCal gratuito como rede de segurança imediata na Fase 01 (bloqueia datas, evita overbooking óbvio, custo zero, é rápido de construir) e migrar para Beds24 na Fase 05 quando o volume de reservas da Algas Marinhas justificar a automação completa.

e.Arquitetura proposta (em fases)

Fase 1: painel e site do cliente já compartilham a mesma fonte de dados. Fase 2: uma camada de channel manager plugada ao Lumina resolve Booking.com/OTAs sem o Lumina precisar de certificação própria.

f.O que construir em cada fase

  • Fase 1 (MVP, custo zero): API pública de leitura (quartos, tarifas, disponibilidade, pacotes, dicas) + reserva direta pelo site indo para a mesma tabela Reservation do painel. Em paralelo, o Lumina importa o feed iCal gratuito da Booking.com para bloquear datas automaticamente (sem detalhes da reserva). Reservas feitas na extranet da Booking.com continuam sendo lançadas manualmente no Lumina pelo admin — tela dedicada para isso, rápida, tipo "dar entrada em reserva externa", usando o bloqueio do iCal como aviso de que há algo para lançar.
  • Fase 2 (sincronização real, Beds24): assinar o Beds24 (≈US$ 9/mês por propriedade) e desligar o iCal. O Lumina passa a empurrar tarifas/disponibilidade automaticamente e receber reservas da Booking.com via webhook, com dados completos do hóspede, caindo na mesma tabela Reservation com uma origem marcada (source: "booking.com").
  • Fase 3 (escala): se o volume de clientes/reservas justificar o custo e o esforço de homologação, avaliar conexão direta com a Booking.com Connectivity API ou upgrade para Channex/SiteMinder — só faz sentido depois que a Fase 2 já provou o modelo com clientes reais.

Fontes: Booking.com Connectivity APIs, Booking.com — limites do iCal, StayNTouch — arquitetura de sincronização em tempo real, Beds24 — programa de reseller/white-label, Beds24 — conectar PMS via API, NOBEDS — tiers de preço e API, NOBEDS — reviews independentes, Comparativo de preços de channel managers 2026.

  1. Aprovar a sequência de fases da seção 04, ou reordenar algo com base em prioridade de negócio (ex: se site público sem sincronização automática com Booking.com já resolve o próximo cliente, a Fase 05 pode esperar).
