01

Modelo de dados

Tudo aditivo sobre o schema atual — nenhuma tabela existente perde campos, só ganha. TableRoom e Reservation continuam sendo a base; o que entra é a camada de conteúdo de vitrine e a camada de sincronização externa.

a.Organization — tipo, contrato e site

model Organization {
  // já existe, muda só o significado:
  tipo            String   @default("pousada")
  // "pousada" | "pousada_restaurante" | "restaurante"

  // novo — gestão de contrato de verdade:
  contractStatus  String   @default("ativo")
  // "ativo" | "inativo" | "inadimplente"
  contractStart   DateTime?
  contractEnd     DateTime?

  // novo — site público:
  siteSlug        String?  @unique   // ex: "algas-marinhas"
  sitePublished   Boolean  @default(false)

  roomContents    RoomContent[]
  packages        Package[]
  tips            ContentTip[]
  paymentMethods  PaymentMethod[]
}

b.Conteúdo de vitrine — novo, um por TableRoom

model RoomContent {
  id              String   @id @default(uuid())
  tableRoomId     String   @unique
  descricaoLonga  String?
  fotos           Json     // array de URLs
  tarifaBaixaTemp Float?
  tarifaAltaTemp  Float?
  tableRoom       TableRoom @relation(fields: [tableRoomId], references: [id])
}

model Package {
  id, organizationId, nome, descricao
  precoPromocional Float?
  vigenciaInicio, vigenciaFim DateTime?
  ativo Boolean @default(true)
}

model ContentTip {
  id, organizationId
  tipo    String   // "passeio" | "transfer"
  titulo  String
  descricao String?
  ordem   Int @default(0)
}

model PaymentMethod {
  id, organizationId
  tipo        String  // "pix" | "cartao" | "dinheiro" | "transferencia"
  instrucoes  String?
  ativo       Boolean @default(true)
}

c.Sincronização externa — iCal hoje, Beds24 amanhã

model IcalFeedConfig {
  id             String   @id @default(uuid())
  tableRoomId    String   @unique
  importUrl      String   // export ICS da Booking.com para este quarto
  lastSyncedAt   DateTime?
  lastSyncStatus String?  // "ok" | "erro"
}

model ExternalCalendarBlock {
  id            String   @id @default(uuid())
  tableRoomId   String
  source        String   @default("booking_ical")
  externalUid   String   // UID do evento ICS, evita duplicar no re-sync
  checkin       DateTime
  checkout      DateTime
  reservationId String?  // preenchido quando o admin lança a reserva de verdade
  importedAt    DateTime @default(now())

  @@unique([tableRoomId, externalUid])
}

Reservation ganha só um campo: source String @default("painel") ("painel" | "site" | "booking_ical") — para saber de onde cada reserva veio sem quebrar nada que já existe.

02

Backend — o que muda

a.API pública (sem autenticação, por siteSlug)

GET
/api/public/:orgSlug/siteOrganização + quartos com conteúdo + pacotes + dicas + formas de pagamento. Retorna 404 se sitePublished=false ou 503 se contractStatus≠"ativo".
GET
/api/public/:orgSlug/rooms/:roomId/availabilityDisponibilidade combinando Reservation ativas + ExternalCalendarBlock do quarto.
POST
/api/public/:orgSlug/reservationsCria Reservation com source:"site", status "reservado" — pendente de confirmação do admin (sem gateway de pagamento na Fase 01).
GET
/api/public/:orgSlug/rooms/:roomId/calendar.icsExporta as reservas do Lumina em ICS — o admin cola essa URL na Booking.com para bloquear lá o que foi reservado no site.

b.API autenticada — novo

PUT
/api/organizations/:id/contractSuper admin: contractStatus, contractStart, contractEnd.
PUT
/api/organizations/:id/site-settingssiteSlug, sitePublished.
GET/PUT
/api/room-contents/:tableRoomIdFotos, descrição, tarifas por temporada.
CRUD
/api/packages · /api/tips · /api/payment-methodsEscopados por organizationId via orgFilterMiddleware já existente.
CRUD
/api/ical-feedsCadastrar a URL de export ICS de cada quarto + POST /:id/sync-now.
GET
/api/external-calendar-blocks?unlinked=trueBloqueios da Booking.com que ainda não viraram uma Reservation — a fila de "lançar manualmente".

c.Middleware de contrato

Extensão do orgFilterMiddleware existente: se contractStatus≠"ativo", bloqueia rotas autenticadas normais do painel (como hoje) e faz a API pública responder 503 para aquele siteSlug — o site do cliente inativo para de aceitar reserva automaticamente, sem precisar de um passo manual separado.

04

O site como motor de tema, não um projeto por cliente

O layout já provado da Algas Marinhas vira um conjunto de componentes React que leem da API pública — a "pele" (cores, fontes, fotos, texto) é dado; a estrutura (hero → sobre → quartos → gastronomia → localização → avaliações → CTA) é o motor, igual para todo cliente novo.

05

Integração iCal gratuita — como funciona de verdade

Importação: Lumina lê o ICS de export da Booking.com e cria bloqueios de data. Exportação (linha pontilhada): o Lumina também gera um ICS próprio para a Booking.com importar, para reservas feitas direto no site bloquearem lá também.

a.Limitações reais, ditas sem rodeio

  • O feed da Booking.com só traz datas bloqueadas — sem nome, contato ou valor do hóspede. O admin sempre completa isso manualmente olhando a extranet.
  • Atraso de até 12h do lado da Booking.com — o job do Lumina pode rodar a cada 30-60min, mas isso não acelera o lado deles.
  • Só funciona enquanto a Algas Marinhas não tiver um channel manager certificado ativo — no dia de migrar para o Beds24 (Fase 05), o IcalFeedConfig é desativado.
  • Exige checar se a Algas Marinhas tem no máximo 1 unidade por tipo de quarto — critério de elegibilidade da própria Booking.com para importar/exportar calendário.
Critério de aceite da Fase 01 Uma reserva feita na Booking.com aparece como bloqueio em até 1h da sincronização rodar; uma reserva feita no site do Lumina aparece bloqueada na Booking.com depois do admin colar a URL de export; nenhuma reserva duplicada quando o admin lança manualmente a partir de um bloqueio já existente.

08

Por onde começar

A Fase 01 não depende de nenhuma pendência da seção 07 — pode começar agora mesmo: é só schema e cadastro correto. As Fases 02-04 esperam o conteúdo real chegar. Sugestão de ordem imediata:

Fases 01 a 04 estão completas — backend e frontend, testadas de ponta a ponta em navegador real, não só por API:

  • Cadastro com 3 tipos, contrato, menu e rotas condicionais por tipo de organização.
  • Site público em /reservar/algas-marinhas, com a identidade visual real, fotos reais, gastronomia (café da manhã + Il Cantuccio como parceiro), tarifas de exemplo e formulário de reserva funcional.
  • Painel "Site & Conteúdo" para o admin da pousada editar tudo isso sem SQL — testado ao vivo, incluindo persistência real no banco.
  • Painel "Reservas externas para lançar" — testado ao vivo com um bloqueio simulado, reserva lançada e vinculada corretamente.

O único item que resta é fora do nosso controle técnico: a URL de export ICS da Booking.com, que só a proprietária pode coletar na extranet dela. Assim que ela enviar, a sincronização automática (import) já tem o campo pronto para receber — e o motor de sync (POST /:id/sync-now) já está implementado e testado com feeds ICS reais.

Depois disso, o único passo restante do plano inteiro é a Fase 05 (Beds24) — decisão de negócio (contratar o plano) antes de qualquer trabalho técnico adicional.
